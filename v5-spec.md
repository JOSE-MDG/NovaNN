## 1. Context

NovaNN v5 is a complete rewrite from scratch of the framework core. The goal is to eliminate NumPy dependency as the base for operations and replace it with a native stack with hardware-specialized backends.

The current version (v4) has 80+ operations, full autograd, nn/optim/metrics and serialization — all that functionality is preserved. Only the core changes.

NovaNN v5 also includes full support for the Transformer architecture and its training: base blocks, complete architectures (GPT-style, BERT-style, Seq2Seq), basic tokenizer and NLP training utilities.

## 2. Programming Languages

| Language | Role in NovaNN v5 | Status |
|---|---|---|
| **Python** | User interface — public API, `nn`, `optim`, `metrics`, `text`. Input filtering and validation before passing to core. Eager mode. | v5 |
| **C** | Tensor core, dispatch system, CPU backends (oneDNN, Generic+OpenBLAS), generic kernels with SIMD intrinsics + OpenMP. Operates on memory but never owns it. | v5 |
| **C++** | Autograd engine: `build_topo()`, `run_backward()`, `XxxBackward` classes. Own thread pool for graph parallelism. Non-native dtype structs (F16, BF16, Qint8, QUint8). GPU backends. | v5 (engine + dtypes) /  (GPU) |
| **NASM** | Assembly microkernels for the most critical Generic operations: matmul microkernel, reduction, elementwise hot paths. Multiple versions per SIMD level. | v5 |
| **Cython** | Direct C ↔ Python bridge. No NumPy. Clean bridge — control logic and filtering happens before getting here. Partially generated by codegen. | v5 |
| **Rust** | **Complete** memory management via FFI: allocates, frees, Storage ref counting, lazy allocation, pool allocator. Safe binary serialization. | v5 |

### Responsibility Division Principle

**Rust owns the memory. C/C++ operate on it. Python and Cython filter before reaching the core.**

```
Python  →  public API, input filtering/validation, control logic when possible
Cython  →  clean C ↔ Python bridge, minimal own logic
C       →  Tensor struct, dispatch, SIMD kernels + OpenMP, CPU backends
C++     →  autograd engine, thread pool (graph), non-native dtype structs, GPU backends
NASM    →  critical Generic microkernels — multiple versions per SIMD level
Rust    →  allocates, frees, ref counting, lazy materialization, serialization
```

**Filtering principle:** all complex control logic (shape validation, dtype canonicalization, broadcasting checks) is done in Python or in the Cython bridge **before** calling the C core. Low-level functions only execute — they don't manage control logic unless strictly necessary to avoid FFI overhead.

The C ↔ Rust boundary is via raw pointers (FFI). Rust remains safe internally — only the boundary is `unsafe`. The rules are: **Rust allocates and frees. C never calls `free()` on memory that came from Rust.**

## 3. Supported Platforms and Compilers

### 3.1 Target Architecture in v5

**v5 exclusively supports x86-64** on Linux and Windows. This decision prioritizes simplicity, compatibility and ease of testing. Future versions will expand to ARM.

| Platform | OS | Status |
|---|---|---|
| x86-64 | Linux | ✅ v5 |
| x86-64 | Windows | ✅ v5 |
| ARM64 / Apple Silicon | macOS / Linux | future |
| x86-32 | any | not supported |

### 3.2 Supported Compilers

**Standard GCC and G++.** They are the only compilers supported in v5 — excellent support for OpenMP, x86 intrinsics and compatible NASM code generation.

### 3.3 Supported SIMD Levels

Detection at **compile time** via compilation flags — zero overhead at runtime.

| Level | Flags | Key Capabilities | Note |
|---|---|---|---|
| **SSE4.2** | `-msse4.2` | SSE2/3/4.1/4.2 | **Minimum required** for NovaNN binaries |
| **AVX/AVX2** | `-mavx2 -mfma` | FMA3, VNNI (int8), F16C (f16↔f32) | Recommended |
| **AVX-512** | `-mavx512f -mavx512vnni -mavx512bf16` | Foundation, VNNI, native BF16 | Optimal on modern CPUs |
| **AMX** | `-mamx-bf16 -mamx-int8` | Tile matrix ops | Intel Sapphire Rapids+ |

SSE4.2 is the minimum because it guarantees SSE2 (basic float instructions) plus the necessary extensions for various ops.

### 3.4 Build System

**CMake** is the main build system for all native code (C, C++, NASM, Rust FFI). A well-structured `CMakeLists.txt` that detects the available SIMD level, activates the correct flags, links dependencies by backend and manages conditional compilation:

- Automatic SIMD detection and flag activation
- Conditional compilation by backend (oneDNN, OpenBLAS, Sleef, MKL)
- Integration with Cython via scikit-build
- Integration with Cargo for Rust FFI

## 4. Supported Dtypes

### 4.1 Official Types and Their Implementation

Non-native types in C/C++ are implemented as own structs in C++.

| Dtype | Implementation | Notes |
|---|---|---|
| **f32** | Native C `float` | Universal, never canonicalizes |
| **f64** | Native C `double` | Universal in Generic |
| **f16** | C++ struct from scratch | F16C on AVX2 for hw conversion |
| **bf16** | C++ struct from scratch | Native on AVX-512 BF16 and oneDNN |
| **u8** | Native C `uint8_t` | Quantized inference |
| **s8** | Native C `int8_t` | Quantized inference |
| **s32** | Native C `int32_t` | Standard accumulator |
| **s64** | Native C `int64_t` | Generic covers natively |
| **Qint8** | C++ struct from scratch | Quantized int8 with scale and zero_point |
| **QUint8** | C++ struct from scratch | Quantized uint8 with scale and zero_point |
| **bool** | `uint8_t` internally | Never reaches the backend |

**F8 (float8)** is reserved for future versions.

The C++ structs for F16, BF16, Qint8, QUint8 live in `ncore/src/dtypes/` and define arithmetic operators, conversion to/from f32, and special representations (inf, -inf, nan).

### 4.2 dtype × Hardware Compatibility Lookup Tables

The canonicalization system uses several lookup tables. The policy is in the data, not in if/else:

```c
// Table 1: Can this SIMD level operate natively with this dtype? (CPU)
bool simd_dtype_compat[N_SIMD_LEVELS][N_DTYPES];

// Table 2: Does this backend support this dtype without canonicalization?
bool backend_dtype_compat[N_BACKENDS][N_DTYPES];

// Table 3: what dtype to canonicalize to when there is no native support
DType canonicalize_to[N_BACKENDS][N_DTYPES];

// Table 4: if casting is not convenient, which fallback backend to go to
NovaBackend dtype_fallback[N_BACKENDS][N_DTYPES];
```

**Policy examples:**
- bf16 on SSE4.2 → no native HW support → cast to f32
- f16 on AVX2 → F16C allows hw conversion → cast to f32 to operate
- s64 on oneDNN (Limited) → Fallback
- s64 on Generic → own C kernels cover it natively

### 4.3 Backend Compatibility

✅ native | ❌→X canonicalizes to dtype X | ⚠️ partial support

| dtype | oneDNN | cuDNN | MIOpen | Generic + OpenBLAS |
|---|---|---|---|---|
| f32 | ✅ | ✅ | ✅ | ✅ |
| f64 | ✅* | ✅ | ⚠️→f32 | ✅ |
| f16 | ✅ | ✅ | ✅ | ✅ C++ struct |
| bf16 | ✅ | ✅ | ✅ | ✅ C++ struct |
| u8 | ✅ | ✅ | ⚠️ | ✅ |
| s8 | ✅ | ✅ | ✅ | ✅ |
| s32 | ✅ | ✅ | ✅ | ✅ |

## 5. CPU and GPU Backends

### 5.1 Active Backends (CPU)

| Backend | Library | Target Hardware |
|---|---|---|
| **oneDNN** | oneDNN (Intel oneAPI) | Intel and AMD — detects SSE4.2/AVX2/AVX-512/AMX at runtime |
| **Generic** | C Kernels + NASM + OpenBLAS | x86-64 — correctness floor, covers all dtypes |

**Why a single optimized CPU backend:** oneDNN since version 3.x uses CPUID at runtime — on AMD with AVX2 it uses AVX2, on Intel with AMX it uses AMX. AOCL remains as reserved entry `BACKEND_AOCL` in the enum without active implementation.

| **Sleef** | Vectorized math functions (sin, cos, exp, log) for SIMD kernels |

## 6. Dispatch System

**Principle: double dispatch (backend × dtype)**

### 6.1 The 4 Levels

**Level 0 — Dtype Canonicalization**
Queries the lookup tables. Silently resolves incompatibilities — does not throw errors (except in extreme cases, e.g.: operating with types (f32xu8) etc), promotes to the closest dtype or dispatches to the correct fallback.

**Level 1 — Backend Dispatch**
Function pointer table per operation, indexed by `NovaBackend` enum. O(1) lookup, zero overhead at runtime. Example:

```c
typedef void (*OpFn)(const Tensor *a, const Tensor *b, Tensor *out);

OpFn matmul_table[N_BACKENDS] = {
    onednn_matmul,    // BACKEND_ONEDNN
    generic_matmul,   // BACKEND_GENERIC
    cublas_matmul,    // BACKEND_CUDA
    rocblas_matmul,   // BACKEND_ROCM
    NULL,             // BACKEND_AOCL    (reserved)
};
```

**Level 2 — Fallback Chain**

| Hardware | Priority 1 | Always Available |
|---|---|---|
| Intel CPU | oneDNN | Generic |
| AMD CPU | oneDNN | Generic |
| NVIDIA GPU | cuDNN / cuBLAS | Generic |
| AMD GPU | MIOpen / rocBLAS | Generic |

**Level 3 — Generic Backend**
C + NASM + OpenBLAS + OpenMP. Covers all dtypes, all edge cases.

### 6.2 Policy in Code — Data, Not Logic (Simplified Example)

```c
DType           compat[N_DTYPES][N_BACKENDS];
OpFn            matmul_table[N_BACKENDS];
NovaBackend     fallback_chain[N][MAX_CHAIN];
bool            simd_dtype_compat[N_SIMD_LEVELS][N_DTYPES];
bool            backend_dtype_compat[N_BACKENDS][N_DTYPES];
DType           canonicalize_to[N_BACKENDS][N_DTYPES];
NovaBackend     dtype_fallback[N_BACKENDS][N_DTYPES];
```

## 7. Generic Backend — Internal Design

### 7.1 Global SIMD Flag at Compile Time (Simplified Example)

```c
// ncore/include/simd.h
#if defined(__AVX512F__)
    #define NOVA_SIMD_AVX512
    #define NOVA_SIMD_WIDTH_F32 16
    #include <immintrin.h>
#elif defined(__AVX2__)
    #define NOVA_SIMD_AVX2
    #define NOVA_SIMD_WIDTH_F32 8
    #include <immintrin.h>
#elif defined(__SSE4_2__)
    #define NOVA_SIMD_SSE42
    #define NOVA_SIMD_WIDTH_F32 4
    #include <nmmintrin.h>
#else
    #define NOVA_SIMD_SCALAR
    #define NOVA_SIMD_WIDTH_F32 1
#endif
```

### 7.2 NASM for Critical Microkernels

The operations that are the real heart of deep learning have their most critical parts in NASM. The target is Generic/Fallback — when oneDNN is not available, these ops remain competitive.

**Use cases:**
- `matmul_microkernel` — the innermost loop of matmul (~8×8 or 16×16 blocks depending on SIMD)
- `reduce_sum_f32` — vectorized reduction
- `elementwise_fma_f32` — FMA in the hot path

Multiple versions per SIMD level:

```
ncore/src/ops/asm/
├── matmul_micro_avx512.asm
├── matmul_micro_avx2.asm
├── matmul_micro_sse42.asm
└── reduce_f32_avx2.asm
```

C calls these functions as normal external functions:

```c
extern void matmul_micro_f32(
    const float *A, const float *B, float *C,
    size_t M, size_t N, size_t K);
```

### 7.3 C Kernels with Intrinsics + Tail Loop

```c
void mul_backward_f32(
    const float *grad_out, const float *a, const float *b,
    float *grad_a, float *grad_b, size_t n)
{
#if defined(NOVA_SIMD_AVX2)
    size_t i = 0, n_vec = n - (n % 8);
    for (; i < n_vec; i += 8) {
        __m256 g  = _mm256_loadu_ps(grad_out + i);
        __m256 ai = _mm256_loadu_ps(a + i);
        __m256 bi = _mm256_loadu_ps(b + i);
        _mm256_storeu_ps(grad_a + i, _mm256_mul_ps(g, bi));
        _mm256_storeu_ps(grad_b + i, _mm256_mul_ps(g, ai));
    }
    for (; i < n; i++) {
        grad_a[i] = grad_out[i] * b[i];
        grad_b[i] = grad_out[i] * a[i];
    }
#else
    for (size_t i = 0; i < n; i++) {
        grad_a[i] = grad_out[i] * b[i];
        grad_b[i] = grad_out[i] * a[i];
    }
#endif
}
```

**Sleef for vectorized math functions:**

```c
#include <sleef.h>
// Instead of expf(x) scalar in a loop:
__m256 r = Sleef_expf8_u10avx2(x_vec);  // vectorized exp AVX2, ULP < 1.0
```

### 7.4 Threading

| Context | Strategy | Why |
|---|---|---|
| Elementwise kernels (add, mul, relu, etc.) | **OpenMP** | Data parallelism over loops. One pragma, zero maintenance. |
| Parallel reductions (sum, mean, max) | **OpenMP** | `reduction` clause handles it perfectly. |
| Autograd engine — independent graph nodes | **C++ Thread pool** | Graph parallelism with dependencies. OpenMP is not designed for task graphs. |

**Important considerations**: Some libraries have their own internal threading system, so to avoid over-subscription they must be configured to not overlap with NovaNN threading. For example, if you have 16 threads and NovaNN uses 8, libraries should be configured to only use 8 threads.

## 10. Autograd Engine

### 10.1 Where Each Part Lives

| Component | Language | Why |
|---|---|---|
| `build_topo()` + `run_backward()` | **C++** | Hot path. 1000+ nodes in Python = bottleneck. |
| `Node` | **C++** | Basic graph structure. |
| `XxxBackward` classes | **C++** | OOP to encapsulate saved tensors and gradients. |
| Thread pool (graph parallelism) | **C++** | Task scheduler for independent nodes. |
| `Function`, `Context` | **Python** | Op definition. Not the hot path. |
| Python binding | **pybind11** | `tensor.backward()` calls C++ directly. |

### 10.2 Complete Forward + Backward Flow on CPU (Simple Example)

```
# FORWARD
c = a @ b
    → MatMul.apply(a, b)                              [Python]
        → shapes/dtypes filtering                     [Python/Cython]
        → nova.ops.matmul(a, b)
            → _ops.pyx: dispatch_matmul()             [Cython]
                → dispatch_table[BACKEND_ONEDNN]      [C]
                    → Rust allocates Tensor out        [Rust FFI]
                    → onednn_matmul(a, b, out)        [C + oneDNN]
                → returns PyTensor wrapping out
    → c = Tensor(result, grad_fn=MatMulBackward)

# BACKWARD
c.backward()
    → NCore::build_topo(root)                         [C++]
    → NCore::run_backward(topo)                       [C++]
        → independent nodes → thread pool             [C++]
        → node->backward_fn(grad_out, grad_ins)       [C++]
            → dispatch_matmul_bwd()                   [C]
    → grads accumulated in Tensor.grad                [C + Rust]
```

### 10.3 Node struct in C++ (Simplified Implementation)

```cpp
struct Node {
    std::function<void(const Tensor*, Tensor**)> backward_fn;
    std::vector<Node*>   inputs;
    std::vector<Tensor*> saved_tensors;
    int n_inputs;
};
```

## 11. Codegen

There are multiple template directories, all managed by a central file (`registry.json`) that reads the corresponding JSON rules and requests the appropriate template.

```
native_functions.yaml  →  dispatch: which C/C++ function each op calls on each backend
derivatives.yaml       →  math: derivatives + native backward coverage
```

## 12. Execution Mode and Fusion

### 12.1 Pure Eager in v5.0.0

v5.0.0 is 100% Eager. Automatic fusion of arbitrary patterns requires lookahead over the graph — reserved for `nova.compile()`/`@nova.jit` in v6.

### 12.2 Manual Fusion Available in v5.0.0

The `nn/` modules use fused kernels internally. The user can call them directly via `nova.ops.fused_*`:

| Fused Op | Pattern | Benefit |
|---|---|---|
| `fused_linear_relu` | matmul + bias + relu | 3 passes → 1 |
| `fused_linear_gelu` | matmul + bias + gelu | 3 passes → 1 |
| `fused_mul_add` | a*b + c | FMA, 1 instruction |
| `fused_layernorm` | mean + var + norm | 3 passes → 1 |
| `fused_softmax` | max + exp + sum + div | 4 passes → 1 |
| `fused_attention` | QK^T + scale + softmax + @V | complete kernel |

oneDNN leverages its **post-ops** system to chain activations within the same primitive.

### 12.3 Roadmap

```
v5.0.0  →  Pure Eager + manual fusion in nn/ and nova.ops.fused_*
v6      →  nova.compile()/@nova.jit: automatic pattern detection, graph compilation
```

## 13. Transformer Support

### 13.1 Native Ops in C

- `attention.c` → `scaled_dot_product_attention(Q, K, V, mask, scale, out)`
- `softmax.c` → numerically stable softmax (log-sum-exp)
- `positional.c` → `sinusoidal_pe()`, `rope_encode()`

### 13.2 Python Modules

In `nova/nn/modules/transformer/`: `attention.py`, `feedforward.py`, `positional.py`, `encoder.py`, `decoder.py`, `blocks.py`, `masking.py`.

In `nova/models/`: `gpt.py`, `bert.py`, `seq2seq.py`.

### 13.3 Tokenizer

```
nova/text/tokenizer/: base.py, char.py, bpe.py, vocab.py
nova/text/utils.py
```

## 14. Changes in `nova/` from v4

| Component | Change |
|---|---|
| `autograd/function.py` | `apply()` no longer converts to numpy. Input filtering before calling core. |
| `autograd/engine/engine.py` | `_build_topo()` and `_backward()` logic is handled in C++. Python only has the entry point via pybind11. |
| `autograd/_ops/*.py` | `forward()`/`backward()` use `nova.ops.*`. |
| `autograd/_ops/_attention.py` | New. `ScaledDotProductAttention` backward. |
| `_internal/_binding.py` | No longer reads YAML for Tensor. YAML is exclusive to C codegen. |
| `_tensor.py` | Wraps Cython's `PyTensor`. |
| `.es.md` files | Deleted. Everything now goes in `docs/` |
| `nn/modules/embedding.py` | New. |
| `nn/modules/transformer/` | New. |
| `models/` | New. |
| `text/` | New. |
| `metrics/nlp/` | New. |

## 16. Out of Scope for v5

| Component | Description | Target |
|---|---|---|
| **`nova.compile()/@nova.jit`** | Automatic pattern detection, compiled backend | v6 |
| **Triton kernels** | Flash Attention and GPU fused kernels | v6 |
| **NVIDIA GPU backend** | cuDNN + cuBLAS + CUTLASS | v5 |
| **AMD GPU backend** | MIOpen + rocBLAS via ROCm | v5  |
| **F8 (float8)** | Emerging dtype for inference | future |
| **ARM / Apple Silicon** | NEON and Apple AMX support | future |
| **BLEU / ROUGE** | Generation evaluation metrics | v6 |
